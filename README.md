# 对页 

[简体中文](README.md) | [English](README.en.md)

**教材手写批注与对题** — 一款面向 Android 平板的手写做题应用：把练习册和答案册同屏打开，用触控笔在 PDF 上直接批注，并为当前页的题目自动找到对应答案。

全部处理都在设备内完成，不上传任何文档。

## 关于名字与图标

名字取「对」与「页」两层意思：**对答案**，以及**对开的两页**。产品做的正是这一件事——左边一页题，右边一页答案，由引擎判断哪一条对应哪一题。

图标是同一个想法的几何写法：两页并排，左页缺一个口，右页凸出正好补上，在中线互相咬合。缺口与凸起半径相同、圆心都落在 x=256，所以缩到 24px 仍然读得出「两页彼此相合」。这既是匹配引擎，也是用户真正会去拖动的那条分隔条。图标里没有铅笔、公式或学士帽——那些描述的是学科，不是工具。

## 项目来源（Provenance）

本仓库由两个独立的上游合并而成。两个来源都在下面写明，便于核对与追溯。

### 1. 应用主体（base）

应用主体来自 **LaTeXSnipper Mobile**：

> **https://github.com/strangelion/LaTeXSnipper_mobile**

上游是一款本地 OCR 与公式编辑应用，提供了 Capacitor/Android 封装、PDF 渲染、设置与国际化等基础能力。本仓库最初从它分出。

此后核心部分整体重写，上游的代码已不在其中，许可证也随之由 AGPL-3.0 改为 **MIT**。分界点、判据与仍然保留的出处声明，记在 [docs/许可证变更.md](docs/许可证变更.md)。

### 2. 答案匹配引擎（matching engine）

同屏对题所使用的匹配引擎来自一个独立仓库：

> **https://github.com/LZY0105/Math-answer-to-question-matching-model**

**本软件使用该引擎。** `src/pdf/` 下的 21 个模块直接来自该仓库，与其 `main` 分支保持一致，引擎自带的回归测试也一并移植到了 `test/`。

引擎解决的问题是：两本 PDF 除了印刷内容之外没有任何共同标识符时，判断答案册里的哪一条对应练习册里的哪一题——或者拒绝作答。它按“最便宜的信号优先”分级：书签层级题号 → 目录对齐 → 数学加权相似度 → 有界序列对齐，并且**在两本书未被确认为配套之前不会给出自动答案**。

引擎以 **MIT** 许可证发布（© 2026 LZY0105），与本仓库一致。

## 这个版本做了什么取舍

上游是一款 OCR 应用。本版本把它**精简为手写做题工具**：识别、公式编辑器、模型管理、AI 服务商、识别历史全部移除，只保留“课本”这一条主线及其必需的设置。

被移除的功能连同其代码完整保留在本地分支，未来需要时可以取回：

| 分支 | 内容 |
|---|---|
| `feature/with-ocr-preserved` | 精简前的完整版本（含 OCR、编辑器、模型与 AI 服务商） |
| `feature/ocr-and-editor-preserved` | 更早的完整版本 |

围绕识别栈的周边设施也一并清掉了：模型打包脚本 `scripts/package-models.js` 与调用它的 `package-models.yml`、ONNX 量化脚本 `scripts/quantize.py`、七个 Python 模型测试与它们共用的 `test_utils.py`，以及运行这些测试的 `test/run_tests.sh`。它们全部来自上游，而识别功能删掉之后，它们指向的东西一个都不在了：打包脚本读的 `public/models/` 目录不存在，量化脚本里写死的是另一台机器上的绝对路径，`run_tests.sh` 点名 22 个测试文件、其中 8 个在这次清理之前就已经不在仓库里。测试的唯一入口是 `npm test`。

上游留下的代码也在逐步换掉。整份工程约五万两千行手写代码里，还逐字保留着上游原文的是 **约 700 行、1.3%**——不含 `LICENSE`，也不含 Gradle wrapper、Capacitor 模板、`package-lock.json` 这些换谁跑都一样的生成物。这个数不抄在文档里，`npm run check:upstream` 现算。`src/core/logger.js`、`i18n.js`、`update-checker.js`、下拉选择器与背景动效都已重写，`status.js`、`splash.js`、`constants.js` 因为无人调用而直接删除，iOS 构建那一套（两个脚本加两份 `ExportOptions.plist`）因为在这个工程里从来就跑不起来而整套移除。

重写最初不是为了摆脱许可证，而是因为逐个读过去之后，其中好几处本来就是坏的（清到后来上游的表达确实归零了，许可证也随之改为 MIT，见 [docs/许可证变更.md](docs/许可证变更.md)）：`exportAsZip` 调用了从未加载的 JSZip，「检查更新」查的是上游仓库的发布，下拉菜单的选项文字只在初始化时抄一份、语言一换就停在旧语言上，CI 里那一步用 `sed` 把算好的 `versionCode` 覆盖成一个小两个数量级的值、于是 CI 出的包装不到本地装过的机器上。

**移除 OCR 不影响对题。** 匹配引擎从 PDF 书签树解析题号，只有在题号对不上时才退回文本相似度。在四本真实考研教材上，全程没有任何识别器参与，仍然做到 **508/508 全部解析、零错误、HIGH 置信度 100% 精确率**。

唯一受影响的情形是**既没有书签、文字层也不可读的纯扫描件**——这种文档会明确报告“需要 OCR 后才能匹配”，而不会猜测。

## 核心功能

- **每栏一队内容**：一栏不再只装一份文件。新开的文件或草稿纸插在当前项之前，被它换下来的那一份转到下层——不是关闭，随时可以唤回。切换行上滑取下一项、下滑取上一项；点标题打开本栏内容列表直接选，点选不重排。两栏各自独立循环。
- **同一本书可以同时开在两栏**：题在前面、答案在后面的习题册，不用再来回翻。两栏各记各的页码与缩放，而笔迹是同一份——哪边落笔或擦掉，另一边立刻跟着变。
- **无限草稿纸**：四个方向没有边界，负坐标就是普通坐标，缩放 25%–400%。草稿纸铺满整栏——没有内缩的纸卡、没有投影、没有固定长宽比；单张还可以进入专注模式占满整个工作区。八种底纹（空白 / 点阵 / 方格 / 横线 / 坐标格 / 等距斜格 / 田字格 / 米字格）、四种纸色、间距与导线浓淡可选。样式属于草稿纸本身，跟着它换栏、重启都不变，且从不改动笔迹。
- **跨栏移动**：任何一项都可以放到另一栏的任意位置。整理内容面板里两栏并排，拖手柄或点「移动到…」走的是同一次原子提交——两个队列要么一起变，要么都不变。
- **书架式文档库**：按封面认书，不按文件名查表；点开时那本书自己翻开到目标栏。第一格永远是使用说明，装完软件就在，跟着界面语言走。
- **双文档工作区**：练习册与答案册同屏；分隔条可在 0:10 到 10:0 之间自由拖动，拖到底是**收起**该栏——队列一条不动，留下一个写着还剩几项的恢复按钮；左右可一键互换，互换保留各自的宽度与批注。
- **分栏**：分隔条由中间那枚握柄（带 φ 的胶囊）拖动，握柄之外的整条线不接手势——它纵贯整个工作区，而底栏正是从它经过的那一段向下轻扫收起的，两个手势原本会被同一根手指同时触发。比例一路跟着手指，两端没有磁吸：想要多窄就有多窄，把某一侧关掉需要把分隔条推到工作区边缘。拖动过程中两侧页面按松手后的真实缩放实时显示，因此左右两边的动画是同一个动作，松手也不再跳一下；双击分隔条回到 50:50 的过渡同样逐帧跟随。
- **手写批注**：钢笔 / 铅笔 / 马克笔 / 荧光笔 / 橡皮，压感、颜色、粗细、不透明度可调；批注按页存储，与 PDF 内容严格分层，永不修改原文件。
- **铅笔画的是石墨**：石墨是被刮到纸的纹理上去的粉末，凸起处着色、凹陷处根本没碰到，所以一道铅笔线不是均匀的一条而是密密的一片颗粒。这做不到靠调制笔画宽度——那改的是轮廓，而特征在里面。实现是拿一张固定种子的噪点贴图当橡皮，从实心笔画上抠掉一部分，抠出的孔就是纸没吃到石墨的地方。贴图只生成一次（否则一平移一缩放，笔迹上的颗粒就重新洗牌，整篇字会在纸上爬），并且随页面而非屏幕缩放（颗粒属于纸）。
- **套索**：圈选批注后可整体移动、缩放、旋转；旋转与缩放共用选区中心，一个手势即可同时完成。整段手势只占一步撤销。圈完之后线旁浮出一条：复制、剪切、换颜色、删除；剪下来的能粘到另一页、另一栏，或者草稿纸上。
- **工具栏四角吸附**：浮动工具栏可拖到任意一边；拖近四角时收起的圆形令牌会胀大提示，松手即被吸入该角并展开。四角各自是独立目标，不再靠“最近边”四舍五入决定落点。
- **自动对题**：按页列出题号与匹配到的答案位置，并标注可靠度；两本书未被确认配套时只提示“请核对”，绝不冒充确定答案。答案册按**关联**查找，不是“另一侧碰巧开着的那本”——关联绑在习题册上，与左右无关；答案册被压在草稿纸下面照样能查，索引与前台渲染是分开的，查一次不动任何一栏正在显示的东西。
- **保存批注**：批注默认 400ms 自动保存，工具栏另有显式的「保存」按钮——有未写入的修改时才可点击，因此灰掉本身就是“已保存”的状态。
- **手写优先的输入**：触控笔只用于书写，手指与鼠标用于平移与翻页。一根手指的含义由页面自己决定：捏放大到超出面板时滑动查看，页面本来就装得下时翻页——按手势起始的方向判定一次，中途不会改变，滑到页面边缘之后的下一次轻扫才翻页。
- **收起工具栏**：顶部导入栏向上、底部胶囊栏向下轻扫即可收起，从对应的屏幕边缘反向轻扫叫回来，两条互不相干。角落里原本有一枚箭头按钮做同样的事，已经删掉——它是这块屏幕上唯一与阅读无关的控件，而且就浮在它正在腾出的那一页上。
- **两套皮肤，两种材质**：**对页 · 液态玻璃**与**对页 · 纸**。后者不是把玻璃的灯关掉，而是另一种材质：玻璃靠透光与折射分层，纸靠明度差与一条切边——桌面比纸暗一档（白页才落得下去），切边是墨色的低透明度而非灰（这块屏幕上其余一切都是墨，中性灰会读成印刷线），影子只给真正悬空的东西。两套皮肤定义完全相同的 44 个令牌，缺一个，那个面就会悄悄落回另一套的取值。
- **不能把可读性押在模糊上**：凡是浮在文档上、又要被阅读的表面，都得自己不透明。这条最初是被一次误诊逼出来的——`backdrop-filter` 在真机上计算为 `none`，而 `CSS.supports` 报告支持，于是被记成了 WebView 的毛病。真正的原因是 CSS 压缩器：样式表里每条玻璃规则都手写了 `-webkit-` 前缀，lightningcss 把两种写法当成同一个属性、按「后写的赢」去重，产物里只剩前缀版，而这台 WebView 恰好只认无前缀那个。去掉手写前缀交给它自己生成之后，25 处玻璃全部生效。
  结论反倒留下了：横贯全屏的顶栏与底栏**故意**不磨砂——它们后面是正在读的那几行字。其余浮在自己那一栏边缘的表面（页码条、栏工具条、缩放牌）保留玻璃。
- **为平板而调**：页面本身禁止缩放（捏合只归 PDF 面板，避免两级缩放争抢同一手势）；手掌搭在屏幕上不会选中文字或弹出长按菜单；越界拖动不会带动整个应用。
- **按压回弹**：胶囊控件按下即压缩，松开时按真实阻尼弹簧（response 0.34s、阻尼比 0.52，采样为 CSS `linear()`）回弹后落定。
- **不打扰**：版本更新改为**默认关闭**。检查更新原先在每次启动后自行运行，并把整屏更新日志盖在当时屏幕上的任何东西之上——包括刚导入文件时那个「这份文件是？」的提问框，于是那个问题就没法回答了。设置里的「自动检查更新」仍可打开，旁边的「检查更新」按一次查一次。
- **无障碍**：支持降低透明度、提高对比度、减少动态效果——以上动效在“减少动态效果”下全部退化为无位移。

## 技术栈

| 层 | 技术 |
|---|---|
| Web UI | Vite 8、Rollup 4、Capacitor 8 |
| PDF | pdfjs-dist（本地 vendored） |
| 批注 | 自研矢量墨迹层（`src/ink/`），IndexedDB 持久化 |
| 队列 | `src/pdf/deck-state.js` — 纯函数，一栏一个有序队列加一个当前项 |
| 草稿纸 | `src/scratch/` — 世界坐标相机、按可见区域绘制的底纹、复用同一个墨迹层 |
| 对题 | 上述匹配引擎，纯 JavaScript，无依赖 |
| 本地存储 | IndexedDB（PDF 字节、笔迹、草稿纸）＋ localStorage（会话、阅读位置、配套关联） |
| 离线 | Service Worker（`public/sw.js`） |
| 多语言 | 自研扁平词表（`src/core/i18n.js`），简体 / 繁体 / English |

多语言目前覆盖设定页与浮动笔迹栏；「练习」这一屏的其余部分（工作区外壳、答案面板、匹配理由）词条已经写好——三个语言文件各 324 条——但接线还没做完，那部分文字暂时仍是硬编码的中文。日文与韩文撤掉了，i18n 那一层没动：把词表放回 `src/core/lang/`、在 `LANGUAGES` 里加一行就回来。

有一类中文明确不会翻译：`question-id`、`body-structure`、`outline-classify`、`pair-verifier`、`toc-filter`、`glyph-map` 六个文件里的中文是正则——「例题|习题|第X题」「答案|解答|证明」「目录|索引」——它们是引擎用来解析中文教材的模式，不是显示给人看的文字。翻译掉它们，题号识别与配套判定会当场失效。

预缓存的只有 6 项：首页、manifest、图标、pdf.js 及其 worker、KaTeX 的样式表。刻意不在其中的有两类：一是 Vite 产出的应用包，文件名带内容哈希、每次构建都变，本来就没法静态列出（fetch 走网络优先，顺手写进缓存——对一个应用包来说这也是更正确的策略，陈旧的包比慢的包更糟）；二是 168 个字符映射表、16 个标准 PDF 字体和 20 个 KaTeX 字形共 204 个文件，只有文档真的用到时才取，预缓存它们等于把首次启动花在多数人永远不会打开的文件上。

这张表出过一次真实故障：它曾经有 17 项，其中 13 项指向已经随识别栈删掉的文件（ONNX 运行时、公式识别模型）。每一项都被单独 catch 并警告，所以没有报错，只是每次安装打印十三条警告然后缓存了四个文件——而没有人读安装日志。现在 `test_ui_interactions.js` 盯着它：表里每一项都必须在源码树里真的存在。

`/vendor/` 下的东西是缓存优先的：它们是钉在仓库里的第三方构建，在同一个应用版本内不会变，缓存里的副本永远是对的答案。

## 原生层与 Agent 的现状

仓库里有 `src/agent/`、`src/native/`、`native/agent-proxy/` 和 `android/app/src/main/cpp/`，看起来像两套已经接好的东西。**它们都还没有工作，而且是两套互不相通的机制**——先说清楚，免得往错的那一套上加代码。

**① 进程内的 JNI 桥**（`libduiye_proxy.so`，随 APK 走）。三个位置：`agent`、`ocr`、`match`，都还空着——问它，它诚实地回 `UNIMPLEMENTED`。开机会探测一次并写进日志（设定 → 开发者选项 → 查看日志），所以「这一层还活着吗」在真机上看得见，不用连调试器。

`match` 那一位和另外两位不一样：答案匹配**现在就有实现**，在 JS 那边。那个位置是留给以后把计算搬到 C++ 的，JS 这一侧的口子已经开好（`preparePair({ matcher })`，契约在 `src/pdf/native-matcher.js`）。**闸门不经过那一层**——角色判定、配对身份、OCR 上限、区域选择都留在 `matching-engine.js`，而且它会对交回来的每一条结论再钳一次。换句话说：交出去的是计算，不是判断。

**② 本机 HTTP 代理**（`agent-client.js` → `127.0.0.1:8787` → `native/agent-proxy/`）。Agent 面板走的是这一条。但那个 C++ 程序**没有被打进 APK**——Android 的 CMake 只编 JNI 那两个源文件，`native/agent-proxy/` 是另一个 CMake 工程，没有构建步骤打包它、也没有代码启动它。所以平板上那个端口没人在听，Agent 面板按下去总是「无法连接本地 Agent 代理」。它是开发期的原型：在电脑上跑起来，再 `adb reverse tcp:8787 tcp:8787` 转过去。

要接 OCR，走 ①。

## 开发与测试

```bash
npm install
npm run dev
npm run build
npm test              # 38 个测试文件，一条命令，全绿或者不绿
```

另有两个检查，都是一次真实故障留下来的：

```bash
npm run check:licenses   # 会进 APK 的依赖，许可证是否与 MIT 相容
npm run check:upstream   # 还有多少行逐字来自上游，按可改写程度分档
```

`check:licenses` 挡的是 copyleft 依赖：混进来一个，整份作品就得跟着它走，而 `LICENSE` 写的是 MIT。这种错误不会让构建失败、不会让测试变红、装出来的包跑得好好的——只有专门去查才看得见。

`check:upstream` 需要一个指向上游的远端；没有就先加，push 地址故意设成无效值防手滑：

```bash
git remote add upstream https://github.com/strangelion/LaTeXSnipper_mobile.git
git remote set-url --push upstream no-push-to-upstream
git fetch upstream
```

真实教材语料（`corpus/`）属于受版权保护的教材文本，**不随仓库分发**；缺少语料时相关测试会自动跳过，`npm test` 仍然通过。若要跑全量回归，将语料放在 `corpus/data.json`，或用 `FIND_ENGINE_CORPUS` 指向它。

Android 构建需要 JDK 21、Android SDK 36。全新 clone 即可直接构建，无需子模块、
无需手工放置任何二进制依赖：

```bash
npm run build:android
cd android && ./gradlew assembleDebug
```

Gradle 工程曾引用两项仓库里没有的依赖（`llama.cpp` 子模块与
`onnxruntime-genai-android-0.6.0.aar`），因此旧版本的全新 clone 无法构建。二者
都属于已经移除的识别（OCR）功能栈，Web 端并不使用，现已连同 `app/ocr` 下的
Java 实现一并删除。
